## AIに「きれいにして」は危険

Cursor や Copilot に「このコードをリファクタリングして」と頼んだことがある人は多いはず。

でも、その結果を **正しいかどうか判断できますか？**

AI はリファクタリングのパターンを大量に知っています。しかし「なぜそのパターンを選んだか」は説明しません。結果だけ見て「きれいになったな」と思っても、本当に品質が上がったかどうかは別の話です。

リファクタリングの原則を知っていれば、AI への指示が的確になり、出力の品質を判断でき、そして何より **自分のコードへの理解が深まります**。

## 原則1: テストがないコードはリファクタリングするな

Martin Fowler『リファクタリング』の大前提です。

```typescript
// ❌ テストなしで構造を変える = 動作保証なし
function processOrder(order: Order) {
  // 200行のモノリシック関数
  // AIに「分割して」と頼むと...正しく動く保証がない
}

// ✅ まずテストを書く → 安心してリファクタリング
describe("processOrder", () => {
  it("正常な注文を処理できる", () => { /* ... */ });
  it("在庫切れなら例外を投げる", () => { /* ... */ });
  it("割引コードを正しく適用する", () => { /* ... */ });
});
```

AI に頼む前に `npm test` が通る状態を作る。これが最初のステップです。

## 原則2: 新機能追加とリファクタリングを混ぜるな

Kent Beck の「帽子を被り替える」メタファーです。

- **リファクタリングの帽子**: 動作を変えずに構造を変える
- **機能追加の帽子**: 構造を変えずに動作を変える

```
# ❌ 1つのコミットで両方やる
git commit -m "注文処理をリファクタリングし、ポイント機能を追加"

# ✅ 分ける
git commit -m "refactor: processOrderを3関数に分割"
git commit -m "feat: ポイント付与機能を追加"
```

AI に頼む時も同じです。「リファクタリングして、ついでにこの機能も追加して」は事故の元。

## 原則3: 小さなステップで進めろ

一度に全部変えない。1つの関数を抽出したら、テストを通す。次のステップに進む。

```typescript
// Step 1: 変数名を改善
const d = getDate(); // → const orderDate = getDate();

// Step 2: 条件式を関数に抽出
if (order.total > 10000 && order.isPremium && !order.isCancelled) { ... }
// → if (isEligibleForDiscount(order)) { ... }

// Step 3: 重複を除去
// 3箇所で同じ計算をしていたら、1つの関数にまとめる
```

AI に「全部一気にリファクタリングして」と頼むと、差分が巨大になって何が変わったかわかりません。

「この関数だけ」「この変数名だけ」と 1 ステップずつ依頼する方が、結果的に速いです。

## 原則4: コードの匂い（Code Smells）を知っておけ

Fowler が定義した「コードの匂い」は、リファクタリングのトリガーです。代表的なものを 5 つ：

| 匂い | シグナル | 対処パターン |
|------|---------|-------------|
| **長すぎる関数** | 20行超 | Extract Method |
| **巨大クラス** | 責任が3つ以上 | Extract Class |
| **重複コード** | 3回以上の重複 | Pull Up / Extract |
| **フラグ引数** | `process(data, true, false)` | Replace with polymorphism |
| **データの群れ** | 常にセットで渡される引数群 | Introduce Parameter Object |

これを知っていると、AI に「この関数は Long Method の匂いがあるから Extract Method して」と言えます。

「リファクタリングして」と「Extract Method で calculateShipping を抽出して」では、AI の出力精度が **全く違います**。

## 原則5: 重複は3回目で抽出しろ（Rule of Three）

DRY 原則（Don't Repeat Yourself）は有名ですが、**早すぎる抽象化** も同じくらい危険です。

```typescript
// 1回目: そのまま書く
const tax = price * 0.1;

// 2回目: 「似てるな」と思うが、まだ我慢
const shippingTax = shippingCost * 0.1;

// 3回目: ここで抽出
function calculateTax(amount: number, rate: number = 0.1): number {
  return amount * rate;
}
```

2回の重複で関数を作ると、後から「実は微妙に違う処理だった」と気づくことが多い。3回目で共通パターンが見えてから抽出する方が、正しい抽象化になります。

## AI への指示テンプレート

これらの原則を踏まえると、AI への依頼はこう変わります：

```
❌ 「このコードをリファクタリングして」

✅ 「この関数には Long Method の匂いがある。
   以下の制約で Extract Method してほしい：
   1. 動作は変えない（既存テストが通ること）
   2. 各関数は20行以内
   3. 関数名は処理内容を明確に表す
   4. 新機能は追加しない」
```

指示の解像度が上がると、AI は **10 倍正確なコードを返してきます**。

## まとめ

| 原則 | 一言 |
|------|------|
| テストファースト | テストなしのリファクタリングは博打 |
| 帽子を分ける | リファクタリングと機能追加は別コミット |
| 小さなステップ | 1回の変更は1つだけ |
| 匂いを知る | 匂いの名前を知ると指示が的確になる |
| 3回目で抽出 | 早すぎる抽象化は負債になる |

AI にコードを任せる時代だからこそ、「なぜそう変えるのか」を理解していることの価値が上がっています。
